================================================================================
PROMPT 05 - PLN-013: Role-based state transitions (enforced in API and UI)
================================================================================
Priority:      P0 - build from scratch
Type:          Backend enforcement + frontend behaviour
Depends on:    PROMPT 01 (roles), PROMPT 03 (workflow engine)
Branch:        feature/PLN-013-role-based-transitions
Estimated:     6-8 dev days

--------------------------------------------------------------------------------
OBJECTIVE
--------------------------------------------------------------------------------
Make the `allowed_roles` field on WorkflowTransition authoritative:
only QA can move a Bug from In Testing to Tested, only QA/Admin can close it,
and every role restriction is enforced server-side on every path that can change
state. The UI must never offer a transition the API will reject.

--------------------------------------------------------------------------------
WHAT ALREADY EXISTS AFTER PROMPT 03
--------------------------------------------------------------------------------
- WorkflowTransition.allowed_roles (list of role keys, [] = any contributor).
- transition_issue() service and allowed-transitions endpoint.
- Basic role reading in the service.

This prompt replaces the basic check with the capability service from PROMPT 01
and closes every bypass.

--------------------------------------------------------------------------------
PERMISSION RESOLUTION
--------------------------------------------------------------------------------
Effective permission for a transition:

  allowed =
      user has capability work_item.transition in the project
      AND (
          transition.allowed_roles is empty
          OR user's effective project role key is in transition.allowed_roles
          OR (transition.admin_override AND user is project or workspace admin)
      )

Rules:
  - Use the project role, not the workspace role, when both exist. Workspace
    admin always resolves to admin.
  - Viewer and Guest never have work_item.transition. Deny at the capability
    layer before the transition check; return 403 with a generic message.
  - A service-token bot user is subject to the same matrix. Do not add a
    bypass for is_service tokens.
  - An admin override is allowed only when transition.admin_override is true.
    Log it: actor, issue, from, to, transition, reason "admin_override".
  - Do not reveal the whole workflow to unauthorised users. The allowed list
    contains only transitions the user can perform.

--------------------------------------------------------------------------------
ENFORCEMENT POINTS
--------------------------------------------------------------------------------
Every path that changes Issue.state_id must call transition_issue (PROMPT 03).
Audit and fix these:

  apps/api/plane/app/views/issue/base.py            partial_update, create
  apps/api/plane/api/views/issue.py                 update
  bulk update flow in the web app                  one PATCH per item today; a
    future server-side bulk endpoint must call the service per item
  apps/api/plane/app/views/cycle/issue.py           transfer-issues
  apps/api/plane/app/views/intake/base.py           accept (initial state only)
  CE v1.4.2 has no importer view; add one only if the importer feature is in
    scope, and then use source=import
  apps/web board drag -> PATCH (no separate backend path)
  future automations -> system actor, explicit capability

Add a CI guard (see PROMPT 03) that greps for direct state assignment outside
the allowlist. Allowlist: transition service, migrations, tests, data repair
commands.

--------------------------------------------------------------------------------
ERROR CONTRACT
--------------------------------------------------------------------------------
Role denial returns 403, never 400:

  {
    "error": {
      "code": "transition_forbidden",
      "message": "QA or Admin can move this bug to Tested.",
      "details": {
        "issue_id": "uuid",
        "from_state_id": "uuid",
        "to_state_id": "uuid",
        "required_roles": ["qa", "admin"],
        "allowed_transitions": [
          {"to_state_id": "uuid", "to_state_name": "In Progress"},
          {"to_state_id": "uuid", "to_state_name": "Rejected"}
        ]
      }
    }
  }

Other codes:
  400 transition_not_allowed  (no such edge in the workflow)
  400 comment_required
  400 fields_required
  409 stale_workflow
  403 transition_forbidden
  503 workflow_unavailable (state change only; other edits still work)

Keep the existing DRF error shape for endpoints that already use it. If the
project uses a different envelope, wrap the new error consistently and document
it in the API guide.

--------------------------------------------------------------------------------
ALLOWED-TRANSITIONS ENDPOINT
--------------------------------------------------------------------------------
  GET /api/workspaces/<slug>/projects/<pid>/work-items/<issue_id>/allowed-transitions/
  GET /api/workspaces/<slug>/projects/<pid>/workflows/<wid>/allowed-transitions/?issue_id=

Response:
  {
    "issue_id": "uuid",
    "current_state_id": "uuid",
    "current_state_name": "In Testing",
    "workflow_id": "uuid",
    "transitions": [
      {
        "to_state_id": "uuid",
        "to_state_name": "Tested",
        "to_state_group": "started",
        "requires_comment": false,
        "required_fields": [],
        "allowed": true,
        "reason": null
      }
    ],
    "denied": [
      {
        "to_state_id": "uuid",
        "to_state_name": "Tested",
        "allowed": false,
        "reason": "Requires QA or Admin",
        "required_roles": ["qa", "admin"]
      }
    ]
  }

Rules:
  - `denied` is returned only to project/workspace admins; other users get only
    the allowed list.
  - Never cache beyond the request.
  - It must be safe to call on every item open; index the lookups.

--------------------------------------------------------------------------------
FRONTEND
--------------------------------------------------------------------------------
1. State menu (work item detail and peek overview)
   - Fetch allowed transitions on open and on window focus.
   - Show allowed targets normally.
   - For admins, show denied targets disabled with the reason and a lock icon.
   - For non-admins, hide denied targets entirely.
   - If a required comment exists, open the transition dialog.
   - On 403: toast the server message, refetch the item and the allowed list,
     and restore the previous state (no optimistic ghost).

2. Board (coordinate with PROMPT 10)
   - On drag start, only allowed columns are valid targets.
   - Invalid columns dim and show a tooltip "Only QA can move this to Tested".
   - Do not use colour alone: add a dashed outline and a lock icon.
   - Dropping on an invalid column is blocked locally; if it reaches the server,
     the 403 handling above applies.

3. Workflow builder
   - The transition cell already has role chips from PROMPT 03; add:
       * a lock icon when allowed_roles is not empty
       * an "Admin override" toggle per transition
       * a "Test as role" preview that hides/disables cells for the chosen role
   - Saving a transition writes allowed_roles and admin_override.

4. Activity and audit
   - Successful transition activity shows actor and, for overrides, a badge
     "Admin override".
   - A denied attempt is logged server-side. Do not show denied attempts to
     other users; project admins can see them in the audit log.

5. Accessibility
   - State menu items expose aria-disabled and a description.
   - Drag announcements include "not allowed" for invalid targets.

--------------------------------------------------------------------------------
TESTS
--------------------------------------------------------------------------------
- Parametrised: Bug workflow role x from x to for admin, member, developer, qa,
  viewer, guest.
- API: developer PATCH In Testing -> Tested returns 403 with required_roles;
  qa returns 200; admin with override returns 200 and writes an audit row.
- API: viewer and guest receive 403 for any transition.
- API: allowed-transitions returns only permitted moves for a developer and
  includes denied entries for an admin.
- Concurrency: transition deleted between read and write returns 409.
- Service token: bot user with developer role denied; with qa role allowed.
- UI: menu hides denied states for a developer; board dims the Tested column.
- Audit: denied and override attempts are recorded.
- Guard: direct state assignment outside the service fails CI.

--------------------------------------------------------------------------------
ACCEPTANCE CHECKLIST
--------------------------------------------------------------------------------
[ ] Developer cannot set Tested through UI or API.
[ ] QA can move In Testing -> Tested -> Closed.
[ ] Admin override works only when enabled and is audited.
[ ] Viewer/Guest cannot transition anywhere.
[ ] Every state-changing endpoint uses the service (CI guard proves it).
[ ] 403 responses contain required roles and allowed next states.
[ ] allowed-transitions never leaks denied transitions to non-admins.
[ ] Board and detail menu agree with the API for the same user.
[ ] Tests green; evidence attached (403 curl, menu screenshot).

--------------------------------------------------------------------------------
NON-REGRESSION
--------------------------------------------------------------------------------
- Projects with workflows disabled keep the old state behaviour.
- Admin/Member retain their existing ability to move work items.
- Do not break bulk update for items the user is allowed to move; denied items
  are reported per item, not as a whole-request failure unless atomic=true.
- Do not add role checks to unrelated PATCH fields (title, description,
  priority) beyond the existing work_item.edit capability.
