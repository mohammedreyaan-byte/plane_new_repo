--------------------------------------------------------------------------------
OBJECTIVE
--------------------------------------------------------------------------------
Prove the whole SDLC flow works on a staging deployment that matches
production, and measure performance under a realistic 15-user load with
headroom. Produce repeatable suites that run in CI and on demand, with evidence
that can be attached to the go-live approval.

--------------------------------------------------------------------------------
TEST ENVIRONMENTS
--------------------------------------------------------------------------------
  - Staging: same image digests as production (PROMPT 24), same Postgres major
    version, separate database, Mailpit for email, a mock or sandbox GitHub and
    Slack, seeded data.
  - Production smoke: read-only checks and one disposable test project, never
    destructive tests against real data.
  - Test data seed command:
      python manage.py seed_e2e --workspace e2e --project E2E --reset
    Creates: 6 users (admin, member, developer, qa, viewer, guest),
    4 work item types, 4 workflows, 7 states, 10 labels, 3 cycles (one active),
    3 modules, 5 views, 500 work items across types/states, 200 comments,
    50 attachments (small files), 20 webhooks pointed at a local receiver.
    Deterministic and re-runnable; never run against production.

--------------------------------------------------------------------------------
E2E SUITE (Playwright, TypeScript)
--------------------------------------------------------------------------------
Follow the repo's existing Playwright setup; do not add a second runner.
Location: e2e/ with fixtures and page objects. Run against staging or a local
compose stack.

Scenarios - every one must be automated:

  AUTH AND ROLES
   1. Admin signs in, sees workspace settings.
   2. Developer signs in, cannot see Members, Work item types, Workflows,
      Service tokens, Integrations.
   3. QA signs in, can reach the Bug workflow states.
   4. Viewer sees work items read-only; edit controls are absent and direct API
      calls fail.
   5. Guest sees only their own items.

  TYPES AND WORKFLOWS
   6. Create a Bug with a type; the badge appears in list, board and detail.
   7. Walk a Bug: New -> In Progress -> Code Review -> In Testing -> Tested ->
      Closed as QA.
   8. Developer is blocked at In Testing -> Tested (menu hidden and direct API
      403).
   9. Task, Story and Epic each show their own columns and states.
  10. Type change resets the state and records activity.
  11. Epic with open children cannot be completed without force + comment.

  FILTERS, VIEWS, BACKLOG, BOARD
  12. Filter by type, priority, assignee and state; combine filters.
  13. Group by type; save a View; reload and verify identical results.
  14. Share a View with a second user; verify read-only for non-owner.
  15. Backlog: rank three items, reload, order persists.
  16. Move two backlog items to the active cycle; verify cycle contents and
      state transition.
  17. Board: drag a card to an allowed column; blocked column shows the reason.

  MODULES, CYCLES, REPORTS
  18. Link an Epic to a Module; complete a child; progress updates.
  19. Close a cycle with carry-over; verify the next cycle and burndown.
  20. Open Reports; counts match a filtered work item list; export CSV.

  INTEGRATIONS AND TOKENS
  21. Service token: a script transitions a work item and posts a comment;
      a project-B call returns 403.
  22. GitHub (mock/sandbox): a PR titled "E2E-1 ..." links to the item.
  23. Slack (mock): a state change posts one message; an unselected event does
      not.

  NOTIFICATIONS AND WEBHOOKS
  24. Assign a user; in-app and Mailpit email arrive; the actor gets neither.
  25. Webhook receiver receives a signed event; duplicate delivery does not
      duplicate the link.

  ISOLATION
  26. A member of project A cannot open project B by URL or API (404).
  27. Search for a term in project B as a project-A user returns nothing.

  RESILIENCE
  28. Refresh during a drag does not lose data.
  29. Two users edit the same item; the second sees a conflict or last-write
      result as designed, with no crash.
  30. Session expiry redirects to login and returns to the same page.

Test hygiene:
  - Each scenario is independent and cleans up its data.
  - No fixed sleeps; wait on network or UI state.
  - Screenshots and traces on failure; video retained for 7 days in CI.
  - Run in parallel shards; total runtime under 25 minutes.
  - Retries: maximum 1, and a retry is a flake to be fixed, not ignored.

--------------------------------------------------------------------------------
LOAD AND PERFORMANCE SUITE (k6)
--------------------------------------------------------------------------------
Model: 15 active users, read-heavy with periodic writes, plus one CI bot.
  - 70% reads: list work items, open item, board, cycle, analytics
  - 20% writes: create/update item, comment, transition
  - 10% admin/report/export

Scenarios and thresholds:
  smoke         1 VU, 1 min, all endpoints 2xx
  average       15 VUs, 20 min
  stress        50 VUs, 10 min (find the knee)
  spike         5 -> 50 in 30 s, hold 2 min, back to 5
  soak          15 VUs, 2 hours (memory, connection leaks, queue depth)

Thresholds:
  http_req_failed < 0.5%
  p95 latency: list < 400 ms, detail < 300 ms, board < 800 ms,
               analytics < 1200 ms, create/update < 500 ms, transition < 400 ms
  p99 < 3x p95
  No 5xx under average load
  Worker queue returns to baseline within 5 minutes after the run
  Database connections stay below 80% of max
  Memory stable during soak (no monotonic growth)

Test data and isolation:
  - Dedicated load project with 5,000 work items, 20 states, 500 labels links,
    200 cycles/modules, 6 users.
  - Token-based auth with a service token scoped to the load project.
  - Never point load tests at production or shared staging data.
  - Capture: k6 summary JSON, Grafana/Prometheus snapshots, slow query log,
    EXPLAIN plans for the top 5 slowest queries.

Analysis:
  - Identify the top 5 slow queries and add indexes or fix N+1s.
  - Record before/after numbers in docs/testing/performance.md.
  - Re-run until thresholds pass. If a threshold cannot be met for a documented
    product reason, get written acceptance, do not silently loosen it.

--------------------------------------------------------------------------------
CI INTEGRATION
--------------------------------------------------------------------------------
  - PR job: build, unit, API, web, a fast E2E smoke subset (auth + create +
    transition) against docker compose.
  - Nightly: full E2E against staging, load average scenario, security
    authorization suite (PROMPT 21).
  - Release gate: full E2E green + load smoke green + no open P0/P1 bugs.
  - Artifacts: HTML report, traces, screenshots, k6 JSON, performance diff.
  - Flake tracking: a dashboard of failing scenarios over 14 days; a scenario
    failing more than twice is quarantined and fixed within a week.

--------------------------------------------------------------------------------
ACCEPTANCE CHECKLIST
--------------------------------------------------------------------------------
[ ] Seed command creates a deterministic, isolated test environment.
[ ] All 30 E2E scenarios are automated and green against staging.
[ ] Role, workflow and isolation scenarios fail when the rule is deliberately
    broken (mutation check on at least 3 tests).
[ ] Load average, stress, spike and soak scenarios pass their thresholds.
[ ] The top 5 slow queries are identified and improved or accepted in writing.
[ ] CI runs smoke on PRs and the full suite nightly.
[ ] Release gate is enforced.
[ ] Evidence attached: E2E report, k6 summary, performance before/after, queue
    and DB graphs.
[ ] No test writes to production data.

--------------------------------------------------------------------------------
NON-REGRESSION
--------------------------------------------------------------------------------
- Do not weaken thresholds to pass; fix the code or get written acceptance.
- Do not skip role or isolation tests on the release branch.
- Do not use production credentials in test environments.
- Keep E2E runtime reasonable; a suite nobody runs is worthless.
