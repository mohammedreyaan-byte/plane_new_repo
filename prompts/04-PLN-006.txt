--------------------------------------------------------------------------------
BACKEND WORK
--------------------------------------------------------------------------------
1. Clone:
   POST .../workflows/<id>/clone/
   body {"name": "Bug copy", "issue_type_id": "..."}
   Copies workflow states and transitions in one transaction. The target type
   must not already have a default workflow unless ?replace=true; replace is
   admin-only and archives the old workflow (do not delete rows that activities
   reference).

2. Reset:
   POST .../workflows/<id>/reset/
   Restores the built-in matrix for that type. Requires the workflow to be
   identified as a system default (issue_type key in bug/task/story/epic).
   Returns a diff summary {added, updated, removed}. Items in removed states are
   moved to the initial state only with ?force=true; otherwise return 409 with
   the affected item count.

3. Health:
   GET .../workflows/health/?project_id=...
   Checks:
     - every enabled type has an active default workflow
     - exactly one initial state
     - at least one final state
     - no state unreachable from the initial state
     - no duplicate default workflow per type
     - no item in a state not mapped to its type's workflow
     - no transition referencing a state outside the workflow
   Response: {"healthy": bool, "issues": [{code, type_id, workflow_id, detail}]}

4. Parent/child rules (hierarchy):
   - Epic can be a parent of Story, Task or Bug.
   - Story can be a parent of Task or Bug.
   - Task and Bug cannot be parents of a Story or Epic.
   - Enforce on create/update of parent_id:
       400 invalid_parent_type with a human-readable explanation.
   - A cycle can contain an Epic or its children; keep the current behaviour.
     Do not invent a restriction unless the product owner asks.
   - Completing an Epic (moving to Done) while it has open children:
       default: 400 epic_has_open_children {count, sample_ids}
       with ?force=true and capability work_item.edit: allowed; write an
       activity row and require a comment.
   - Deleting a parent does not delete children; children become unparented and
     keep their type/state.

5. Type change reset:
   When PROMPT 02's type change runs and the new type has a workflow, move the
   item to the new workflow's initial state inside the same transaction and
   record the activity. If the new type has no workflow, keep the state.

6. State API:
   GET /projects/<pid>/states/?type_id=<uuid>
   returns only the states mapped to that type's workflow, ordered by
   WorkflowState.sequence, plus {workflow_id, is_initial, is_final}.
   Without type_id, return the legacy full list (backward compatibility).

7. Workflow import/export:
   GET .../workflows/<id>/export/ -> JSON {name, issue_type_key, states,
     transitions}
   POST .../workflows/import/ with the same shape; validate and create.
   Useful for promoting a workflow between projects; no secrets involved.

  use each state. Creating a state offers "add to workflow(s)".

  - State options come from the type-aware endpoint.
  - Changing type in the detail resets the state; confirm before saving.

    Bugs."

    children list.
