================================================================================
PROMPT 21 - PLN-015: Project isolation validation and hardening
================================================================================
Priority:      P1 - security hardening (do this before any external user access)
Type:          Audit + code fixes + automated authorization test suite
Depends on:    PROMPT 01 (roles), 13 (service tokens), 17 (views), 20 (webhooks)
Branch:        feature/PLN-015-project-isolation
Estimated:     6-8 dev days

--------------------------------------------------------------------------------
OBJECTIVE
--------------------------------------------------------------------------------
Prove and enforce that a user can only reach data in projects they belong to,
that guests only see what they are allowed to see, and that every API surface
(search, exports, attachments, webhooks, integrations, notifications, tokens)
respects project membership. Fix every hole found, and leave an automated
authorization test suite that prevents regressions.

This is not a UI task. A hidden button is not isolation.

--------------------------------------------------------------------------------
THREAT MODEL
--------------------------------------------------------------------------------
Actors:
  - Workspace member who is not a member of the target project.
  - Guest with restricted visibility (own items only).
  - Member of project A attempting to read or mutate project B by id.
  - Service token scoped to project A.
  - Unauthenticated internet user.
  - A user with a valid invitation to a different workspace.

Assets: work items, comments, attachments, cycles, modules, views, pages,
intake, drafts, activity, analytics, exports, webhooks, integrations, tokens,
notifications, search results, counts and error messages.

Invariants:
  I1  Every project-scoped object is readable only by an active member of that
      project (workspace admin included only when they are a project member, or
      via an explicit admin capability that is logged).
  I2  Every mutation requires membership plus the capability matrix.
  I3  Cross-project access returns 404 for object fetch and 403 for
      collection access where existence is not secret.
  I4  Counts, aggregates, search suggestions and exports never leak objects
      from projects the user cannot access.
  I5  Guests see only their own items unless Project.guest_view_all_features is
      true; this applies to every list, detail, comment, attachment, activity,
      search and export path.
  I6  A service token is bound to its workspace and project scope.
  I7  Soft-deleted objects are invisible unless the caller has archive
      permission, and never appear in counts.

--------------------------------------------------------------------------------
AUDIT SCOPE - EVERY ENDPOINT MUST BE CHECKED
--------------------------------------------------------------------------------
Use the URL conf as the source of truth (apps/api/plane/app/urls/,
apps/api/plane/api/urls/, apps/api/plane/space/urls/, apps/api/plane/web/urls.py,
and apps/api/plane/urls.py).

For each endpoint record:
  path, method, auth class, permission class, object lookup, project scoping,
  guest rule, service-token scope, expected status for each actor.

Look especially at:
  - issue list/detail/update/delete, bulk, archive, drafts, intake, relations,
    links, attachments, comments, activity, description versions, sub-items
  - cycles, modules, views, pages, labels, states, estimates, analytics,
    reports, exports, importers, webhooks, integrations, API/service tokens
  - search (workspace and project), recent visits, favourites, notifications,
    notification preferences
  - file/attachment download URLs (signed URLs must expire and be scoped)
  - public/space endpoints and any endpoint using AllowAny
  - graphql or any secondary API surface if present

Grep for red flags and review every hit:
  AllowAny, IsAuthenticated only, .objects.get(pk=...), filter(id=...),
  project_id from the request body, request.data["project"], get_object_or_404
  without a project filter, `permission_classes = []`.

--------------------------------------------------------------------------------
FIXES TO IMPLEMENT
--------------------------------------------------------------------------------
1. Centralise project scoping:
   - A mixin/permission that resolves the project from the URL and asserts
     membership before the view body runs. Apply it to every project-scoped
     view that lacks it.
   - Query helpers: project_issues(user, project), visible_issues(user, project)
     implementing the guest rule once. Replace ad-hoc filters.
   - Never accept project_id from the body when it is in the URL; if both are
     present and differ -> 400 project_mismatch.

2. Guest visibility:
   - One helper is_guest_restricted(user, project) used by list, detail,
     comments, attachments, activity, search, exports and counts.
   - Guest create: allowed; guest edit/delete: own items only.
   - Guest sees the project and cycles/modules only through their own items;
     module and cycle counts must be filtered too.
   - Guest cannot access members, settings, integrations, webhooks, tokens,
     analytics beyond their own scope, or exports of others' data.

3. Object-level ownership:
   - For endpoints that take an object id under a project, always filter by
     project_id = resolved project. A valid id from another project must 404.
   - Parent/child relations (sub-issues, links, comments) validate that both
     ends belong to the same project, or to projects the user can access for
     cross-project links if that feature exists.

4. Aggregates and search:
   - Group counts, analytics totals, dashboard tiles, favourite counts and
     search facets must be computed from the already-scoped queryset.
   - Search must apply the same visibility helper; test that a term matching an
     inaccessible project returns nothing and no count.

5. Attachments and files:
   - Signed URLs expire (default 15 minutes) and are issued only after a
     permission check on the parent object.
   - Direct bucket access is not a substitute for authorization; document the
     bucket policy and require private buckets.

6. Exports and imports:
   - Export jobs record the requesting user and re-check membership at download
     time; a revoked member cannot download a queued export.
   - CSV/JSON exports contain only visible items for the requester.

7. Notifications and webhooks:
   - Notification recipients are filtered by project access at send time, not
     only at creation time (a removed member must not keep receiving).
   - Webhook payloads for project-scoped webhooks include only that project's
     data; workspace webhooks include only projects the webhook owner can
     access? No - workspace webhooks are admin-configured and may include all
     workspace projects; document this explicitly and require admin ownership.

8. Service tokens:
   - Enforce project scope centrally (PROMPT 13), not per view.
   - A token cannot read another workspace even with a valid workspace slug
     guess.

9. Error hygiene:
   - 404 for inaccessible object ids.
   - No stack traces, model names or record counts in 403/404 responses.
   - Consistent envelope: {"error": {"code", "message"}} for new endpoints.

10. Rate limiting:
   - Login, invitation accept, magic link, password reset, webhook receiver,
     token auth failure: rate limit per IP and per account.
   - Do not reveal whether an email exists.

--------------------------------------------------------------------------------
AUTOMATED AUTHORIZATION SUITE
--------------------------------------------------------------------------------
Create apps/api/plane/tests/security/test_project_isolation.py plus fixtures:

  - 2 workspaces, 3 projects, users: ws_admin (member of all), member_a,
    member_b, guest_a, outsider (workspace member, no project), other_ws_user,
    bot token scoped to project A.
  - A factory that creates one object of every project-scoped model in project
    A and B.

Parametrised tests (method x endpoint x actor) asserting the matrix in the
audit table. Minimum coverage:
  - every detail endpoint: owner 200, same-workspace non-member 404,
    other-workspace 404, guest allowed only for own item.
  - every list endpoint: results contain only the actor's project; counts match.
  - every mutation: member 200, non-member 404, viewer 403, guest own-only.
  - search and analytics: no leakage in results or totals.
  - export download after membership removal -> 403.
  - service token project B -> 403; workspace B -> 401/404.
  - attachment signed URL after permission revocation.

Add the suite to CI as a required job. It must fail on any new endpoint that is
not covered; keep an explicit allowlist file for intentionally public routes
with a comment explaining why.

--------------------------------------------------------------------------------
ACCEPTANCE CHECKLIST
--------------------------------------------------------------------------------
[ ] The authorization suite covers every project-scoped endpoint and is green.
[ ] No endpoint accepts project_id from the body when it is in the URL.
[ ] Cross-project object ids return 404; counts and search do not leak.
[ ] Guest visibility is enforced on lists, details, comments, attachments,
    activity, search and exports.
[ ] Service tokens are project- and workspace-scoped centrally.
[ ] Attachment URLs are permission-checked and expire.
[ ] Removed members stop receiving notifications and cannot download exports.
[ ] Rate limits protect auth and webhook endpoints.
[ ] The allowlist contains only genuinely public routes with a reason.
[ ] Evidence attached: the matrix and a sample of failing-then-passing tests.

--------------------------------------------------------------------------------
NON-REGRESSION
--------------------------------------------------------------------------------
- Workspace admins must keep the access they legitimately need; log admin
  access to projects they are not a member of if that behaviour is retained.
- Public/space endpoints and share links keep working; document their exposure.
- Do not break mobile/space apps that use the same endpoints.
- Do not weaken existing permission decorators; add to them.
- Performance: the new scoping must not add a query per item; use joins and
  assert query counts on the main lists.
