--------------------------------------------------------------------------------
WORK ITEM 1 - EVENT CATALOGUE AND EMISSION
--------------------------------------------------------------------------------
Document and emit these events (keep existing ones unchanged):

  project.created, project.updated, project.archived
  issue.created, issue.updated, issue.deleted
  issue.comment.created, issue.comment.updated, issue.comment.deleted
  issue.type_changed            (new; payload: from_type, to_type, state_reset)
  issue.transitioned            (new; payload: from_state, to_state, workflow,
                                 transition, actor, source)
  cycle.created, cycle.updated, cycle.started, cycle.completed
  module.created, module.updated, module.completed
  work_item_type.created/updated/deleted   (new)
  workflow.created/updated/deleted         (new)

Rules:
  - Every payload includes: event, action, timestamp (ISO8601 UTC), workspace_id,
    project_id, actor {id, display_name, type: user|bot|system},
    data {the serialized entity}, delivery_id, schema_version "1".
  - New fields are additive; never remove or rename an existing key.
  - Do not include secrets, tokens, private file URLs, or full descriptions
    beyond the existing behaviour.
  - Emission happens after the transaction commits (transaction.on_commit), so
    a rollback never sends an event.
  - One logical action produces one event. A bulk update produces one event per
    item, not one per field.
  - Actor for system actions is {type: "system"} and for service tokens is the
    bot user with type "bot". Never impersonate a human.

Emit from the service layer (transition service, issue service), not from
serializers.

--------------------------------------------------------------------------------
WORK ITEM 2 - DELIVERY RELIABILITY
--------------------------------------------------------------------------------
  - Per-webhook rate limit: default 60 deliveries/minute, configurable in the
    model (rate_limit_per_minute). Excess is queued, not dropped.
  - Circuit breaker: after 20 consecutive failures, pause the webhook for 30
    minutes and log it; do not deactivate permanently until the existing
    threshold is reached. Notify the owner.
  - Retry policy: network/5xx -> retry with exponential backoff up to 6
    attempts over 24 hours; 429 -> honour Retry-After; 4xx other than 429 -> do
    not retry, mark failed.
  - Timeout 30s (existing). Response body truncated to 8 KB in the log.
  - Reject non-http(s) schemes and private IPs (the existing pinned_fetch does
    this; keep it and add a test).
  - Idempotency: X-Plane-Delivery is stable across retries.
  - Signature: X-Plane-Signature is the hex HMAC-SHA256 of the raw body with
    the webhook secret. Document the exact algorithm in the UI and docs.
  - Secret rotation: POST regenerate creates a new secret; the old secret stays
    valid for 24 hours (store previous_secret and previous_secret_expires_at).
    Return both only once.

--------------------------------------------------------------------------------
WORK ITEM 3 - API AND UI
--------------------------------------------------------------------------------
API additions:
  POST /workspaces/<slug>/webhooks/<pk>/test/        send a signed sample event
  POST /workspaces/<slug>/webhook-logs/<log_id>/replay/
  GET  /workspaces/<slug>/webhook-logs/<webhook_id>/?event=&status=&from=&to=&page=
  GET  /workspaces/<slug>/webhooks/<pk>/deliveries/  summary counts
  PATCH /workspaces/<slug>/webhooks/<pk>/             rate_limit, projects

Validation:
  - URL must be https in production (allow http only for localhost in debug).
  - Secret minimum length 32.
  - At least one event category selected; empty -> 400 no_events_selected.
  - Project-scoped webhook must have at least one project.

UI (settings/(workspace)/webhooks/ + components/web-hooks/):
  - List: URL (truncated), events, projects, status, success rate (24h), last
    delivery, owner, menu (edit, test, rotate secret, pause, delete).
  - Create/edit: URL, event checkboxes grouped by category, project scope (all
    or selected), active toggle, rate limit (advanced), secret display with
    copy and "Regenerate".
  - Test: sends a `webhook.test` event, shows the HTTP status and the first
    500 chars of the response inline.
  - Logs: table with time, event, status code, duration, retry count, delivery
    id; expandable request/response with secret headers redacted; replay button
    for failed entries.
  - Event catalogue: a side panel listing every event, a sample payload, and
    the signature verification snippet (Node and Python).
  - Empty state explains what a webhook is and links to the catalogue.
  - Accessibility: tables are keyboard navigable; status is text, not colour
    only.

Documentation: docs/webhooks.md with the event catalogue, payload schema,
signature verification, retry policy and replay.

--------------------------------------------------------------------------------
TESTS
--------------------------------------------------------------------------------
- Signature verification for every event type with a known secret.
- Additive schema: a consumer reading v1 keys is unaffected by new fields.
- Emission after commit: a rolled-back transaction sends nothing.
- Bulk update emits per item and does not duplicate.
- Rate limit queues; circuit breaker pauses; 429 honours Retry-After.
- 4xx no-retry; 5xx retry; final failure logged.
- Replay sends the same delivery id and body.
- Secret rotation overlap works; the old secret fails after 24h.
- SSRF: private IP, localhost (in production), file:// rejected.
- Logs redact the secret and truncate the body.
- Permissions: only workspace admin can create/rotate/delete; member read-only.
- E2E: create a webhook to a local receiver, transition a bug, verify the
  signature and payload.
- Regression: existing webhook consumers still receive the same v1 payload.
