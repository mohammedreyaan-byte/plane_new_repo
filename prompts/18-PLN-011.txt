--------------------------------------------------------------------------------
WORK ITEM 1 - LIFECYCLE
--------------------------------------------------------------------------------
Define one source of truth for cycle status:

  status = upcoming  if start_date > now
           active    if start_date <= now <= end_date and not closed_at
           completed if closed_at or end_date < now

Add Cycle.closed_at DateTime(null=True), Cycle.closed_by FK User(null).
Derive status on read; do not store a duplicate status column.

Rules:
  - At most one active cycle per project. Opening a cycle whose dates overlap
    an active cycle returns 409 active_cycle_exists with the conflicting cycle.
  - Overlapping upcoming/completed cycles are allowed for planning, but warn on
    create/update: 200 with a warning field, or 409 when ?strict=true.
  - start_date < end_date; max duration 365 days.
  - Closing a cycle sets closed_at and runs a scope snapshot; it does not
    change item states by itself.
  - Reopening requires project admin and clears closed_at.

Scheduled behaviour (Celery beat):
  - Daily task cycle_status_sync: auto-open cycles whose start_date has passed
    when Project.auto_start_cycles is true (new field, default false) and
    auto-close at end_date when Project.auto_close_cycles is true (default
    false). Default off to avoid surprising state changes in production.
  - Emit webhooks cycle.started / cycle.completed and in-app notifications to
    the cycle owner and project leads.
  - Idempotent: running twice does not duplicate events.

--------------------------------------------------------------------------------
WORK ITEM 2 - CAPACITY AND SCOPE
--------------------------------------------------------------------------------
Use the fields from PROMPT 09 (capacity_points, is_capacity_hard_limit) and add
if missing:
  Project.cycle_default_capacity_points PositiveInteger(null)

Behaviour:
  - Adding items to a cycle sums estimates (Estimate points for the project's
    estimate scale). No estimate counts as 0 and is reported separately as
    "n items without estimate".
  - Over capacity: warn in the UI and return capacity_after with overflow; block
    only when the hard limit is on.
  - Scope change: on every add/remove after cycle start, record a row in
    CycleScopeChange(cycle, issue, action: added|removed, actor, at, reason).
    New model, small, indexed by cycle and created_at.
  - Cycle detail shows: committed at start, added during, removed during,
    completed, remaining. Burndown uses the committed line and shows scope
    changes as annotations.
  - progress_snapshot: store a daily snapshot {date, total, completed,
    points_total, points_completed} written by a daily task. Do not recompute
    history from current data.

--------------------------------------------------------------------------------
WORK ITEM 3 - GUIDED CLOSE AND CARRY-OVER
--------------------------------------------------------------------------------
Close-cycle dialog:
  1. Summary: completed, incomplete, cancelled, moved out, items without
     estimate.
  2. Choose an action for incomplete items:
       - move to next cycle (picker of upcoming cycles or create one)
       - move to backlog (backlog_rank at the bottom, PROMPT 09)
       - leave in the completed cycle (default)
  3. Preview the affected list, with select/deselect all.
  4. Confirm applies the action through the existing transfer-issues and
     backlog endpoints, per item results, one transaction per batch of 200.
  5. Items moved to another cycle keep their type and, when the target cycle
     defines a start state, transition through the workflow engine
     (PROMPT 03). Never force an invalid transition; skip and report.

Record "Carried over from <cycle>" in the activity feed and do not duplicate the
IssueCycle history.

--------------------------------------------------------------------------------
WORK ITEM 4 - PERMISSIONS
--------------------------------------------------------------------------------
  - cycle.manage: project admin/member (per PROMPT 01 matrix) can create,
    edit, open, close, delete cycles.
  - Developer/QA can add/remove items in an active cycle but cannot create,
    close or delete cycles unless the capability matrix grants it.
  - Viewer read-only; Guest only sees cycles containing their own items.
  - Deleting a cycle with items requires ?force=true and moves items to the
    backlog without deleting them.
  - Audit: create, open, close, reopen, delete, capacity change -> actor,
    timestamp, diff.
