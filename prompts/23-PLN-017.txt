--------------------------------------------------------------------------------
CURRENT STATE AND GAP
--------------------------------------------------------------------------------
In the running deployment:
  - SMTP is disabled. No application email leaves the stack.
  - The instance admin has an Email settings page at /god-mode/email/ with host,
    port, TLS/SSL, username, password, sender name, sender email and a
    "Send test email" action.
  - Django email settings come from the instance configuration (see
    apps/api/plane/license/utils/instance_value.py -> get_email_configuration,
    and the admin app's email form).
  - Invitations, password resets, magic links, webhook deactivation emails and
    notification emails all depend on this configuration.
  - In-app notifications work; email delivery has never been exercised.

This prompt configures a real relay, proves every email path works end to end,
and produces the evidence required to sign off PLN-016 and go-live.

--------------------------------------------------------------------------------
PREREQUISITES FROM INFRA
--------------------------------------------------------------------------------
Obtain from the infrastructure owner:
  - SMTP host, port and encryption mode (587 STARTTLS recommended, 465 SSL,
    25 only inside the network).
  - Username and password or app password (never a personal mailbox password).
  - Sender address on a dedicated subdomain, e.g. notifications@mail.example.com
    or plane@notifications.example.com.
  - Sender display name: "SDLC Delivery Platform".
  - Whether the relay allows a custom envelope sender and Return-Path.
  - SPF, DKIM and DMARC records for the sending domain (coordinate with
    PROMPT 24). The app only sets From; deliverability is an infrastructure
    concern.

Do not use a free personal mailbox as the production sender. For staging, use a
test relay (MailHog/Mailpit inside the network or a provider sandbox).

--------------------------------------------------------------------------------
CONFIGURATION
--------------------------------------------------------------------------------
1. Staging first:
   - Deploy Mailpit (or MailHog) as a compose service, not exposed publicly.
   - Point the instance email settings at mailpit:1025, no auth, no TLS, and
     verify the UI and the API both send.
   - Confirm the admin "Send test email" returns success and the message appears
     in the Mailpit UI with the correct From, Subject and body.

2. Production relay:
   - Set the SMTP values through the instance admin (database-backed instance
     configuration), not by hard-coding settings.py.
   - If an environment fallback exists, keep it aligned; one source of truth.
   - Store the password only in the instance configuration (encrypted at rest
     where the schema supports it) and in the deployment secret store. Never in
     git, tickets, chat or screenshots.
   - Set the default From address and a Reply-To that a human monitors.
   - Set EMAIL_TIMEOUT to 10 seconds so a dead relay cannot hang workers.
   - Log SMTP responses (code and enhanced status) without logging credentials
     or full message bodies.

3. Sender authentication:
   - SPF: include the relay's sending hosts for the subdomain.
   - DKIM: enable signing at the relay and publish the selector.
   - DMARC: start with p=none and rua reporting, then move to quarantine after
     two weeks of clean reports.
   - Use a dedicated subdomain so a reputation problem cannot affect the
     corporate domain.
   - Verify with a real message: check Authentication-Results shows spf=pass,
     dkim=pass, dmarc=pass.

4. Guard rails:
   - EMAIL_TEST_MODE=true in staging redirects all mail to a single test inbox;
     document how to enable it and how it is disabled in production.
   - Rate limit outbound mail per minute to stay under the relay quota.
   - Hard-bounced addresses are suppressed (PROMPT 14's bounce handling).
   - Do not retry authentication failures; surface them in the admin delivery
     log.

For each: record sender, recipient, subject, timestamp, message-id, SMTP

--------------------------------------------------------------------------------
DELIVERABILITY CHECKS
--------------------------------------------------------------------------------
  - Send to Gmail: message lands in Inbox, not Spam; "Show original" shows
    spf=pass, dkim=pass, dmarc=pass.
  - Send to Microsoft 365: same checks; confirm the message is not quarantined.
  - Check the relay's suppression/bounce dashboard after the run.
  - Confirm links use the public WEB_URL (https://...), not localhost, and that
    they open the correct workspace and item.
  - Confirm unsubscribe only affects the specific event type, not security mail.
  - Confirm no email is sent to a user who has been removed from the project
    (test with PROMPT 14's isolation rule).

--------------------------------------------------------------------------------
FAILURE HANDLING
--------------------------------------------------------------------------------
  - Wrong credentials: admin test shows a clear error, the app keeps running,
    queued mail retries later; no secrets in the error text.
  - Relay timeout: worker does not hang; the delivery log records a timeout.
  - 550/551 hard bounce: mark the recipient, stop retrying, surface it.
  - 421/450 temporary: retry with backoff up to the configured limit.
  - Duplicate prevention: the same activity does not send twice on retry
    (idempotency key per event/recipient).
