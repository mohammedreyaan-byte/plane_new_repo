IMAGE BUILD AND RELEASE
--------------------------------------------------------------------------------
1. CI builds internal images from the fork (PROMPT 22) and tags them with the
   commit SHA and the release version:
     registry.internal/plane-backend:<sha>
     registry.internal/plane-frontend:<sha>
     registry.internal/plane-space:<sha>
     registry.internal/plane-admin:<sha>
     registry.internal/plane-live:<sha>
     registry.internal/plane-proxy:<sha>
   Images are immutable; never rebuild a tag.

2. Deployment compose overrides the upstream images:
     web:    registry.internal/plane-frontend:<sha>
     api:    registry.internal/plane-backend:<sha>
     worker: registry.internal/plane-backend:<sha>
     ... same for space/admin/live/proxy
   Use a docker-compose.prod.yaml override; do not edit the vendor compose in
   place without documenting the diff.
   If the stack uses CUSTOM_BUILD, set it according to the repo's documented
   meaning and pin the SHA. Do not use `latest`.

3. The migrator service must run before api/web start and fail the deployment
   if migrations fail. Keep the vendor entrypoint unless a documented reason
   requires a change.

4. Health checks:
   - /api/health/ (or the repo's health endpoint) returns 200.
   - / returns 200 for web.
   - Worker and beat-worker report liveness through the container health check
     or a Celery ping in the release script.
   - Add a /api/health/ readiness check that verifies database and Redis
     connectivity without exposing versions or credentials.

--------------------------------------------------------------------------------
HTTPS AND REVERSE PROXY
--------------------------------------------------------------------------------
  - The bundled proxy (Caddy-based plane-proxy) terminates TLS.
  - SITE_ADDRESS: the internal domain. If using Let's Encrypt with a private
    host, configure DNS-01 via CERT_ACME_DNS; HTTP-01 will fail.
  - If using an internal CA, mount the CA bundle and trust it in all containers
    that make outbound HTTPS calls (SMTP, GitHub, Slack).
  - Redirect HTTP to HTTPS at the proxy, except a health endpoint used by the
    load balancer.
  - HSTS: enable with a short max-age first, then 1 year after verification.
  - TLS 1.2+ only; disable TLS 1.0/1.1 and weak ciphers. Verify with
    testssl.sh or sslyze and attach the report.
  - WEB_URL, CORS_ALLOWED_ORIGINS, API_BASE_URL and the live server URL must all
    use the https origin. Mixed content breaks the web app; verify the browser
    console has no mixed-content warnings.
  - Secure cookies: SESSION_COOKIE_SECURE, CSRF_COOKIE_SECURE, SameSite=Lax.
  - Set SECURE_PROXY_SSL_HEADER and TRUSTED_PROXIES so Django knows the request
    is HTTPS.
  - Do not expose the database, Redis, RabbitMQ, MinIO or the API container
    ports to the host network. Only the proxy publishes ports.

--------------------------------------------------------------------------------
VPN AND NETWORK
--------------------------------------------------------------------------------
  - Put the host behind the corporate VPN; no public DNS A record if the domain
    is internal, or split-horizon DNS.
  - If a public DNS record is unavoidable, restrict at the firewall to the VPN
    egress range and verify from outside that the connection times out.
  - Egress allowed: the SMTP relay, github.com/api.github.com (if PROMPT 07),
    slack.com (if PROMPT 08), the object store if external, and the OS package
    mirrors. Deny everything else by default.
  - Time sync (NTP) is required for TLS, tokens and webhook signatures.
  - Document the firewall rules in docs/deployment/network.md with a diagram.

SECRETS AND CONFIGURATION
--------------------------------------------------------------------------------
  - Generate a new SECRET_KEY, LIVE_SERVER_SECRET_KEY, POSTGRES_PASSWORD,
    RABBITMQ_PASSWORD, MinIO credentials, and all integration secrets. Never
    reuse the development values.
  - Store them in the deployment secret store (Vault, AWS Secrets Manager, or

  - Document rotation for each secret and who owns it.
  - Set DEBUG=0 and confirm a 500 page does not reveal a stack trace.
  - Disable Django admin or restrict it to the VPN and a named group.
  - Set ALLOWED_HOSTS to the exact hostnames.
  - Set API_KEY_RATE_LIMIT, AUTHENTICATION_RATE_LIMIT and
    WEBHOOK_ALLOWED_IPS/HOSTS to production values.

--------------------------------------------------------------------------------
DEPLOYMENT PROCEDURE
--------------------------------------------------------------------------------
1. Pre-flight: CI green, images pushed, database backup verified (PROMPT 25),
   change ticket approved, maintenance window announced.
2. Pull images by digest, not tag.
3. Run migrations as a one-shot job; capture output.
4. Start api, worker, beat-worker, live, web, space, admin, proxy.
5. Wait for health checks; run the smoke test:
     - log in as an admin
     - open the SDLC project
     - create and delete a test work item
     - open a board and a cycle
     - send a test email (PROMPT 23)
6. Record the release in docs/deployment/releases.md: version, SHA, who, when,
   migrations applied, smoke result.
7. Keep the previous image digests so rollback is a compose revert plus a
   database restore if a migration is destructive.

Rollback:
  - Code-only rollback: redeploy previous digests.
  - Migration rollback: only if the migration is reversible and tested; else
    restore the pre-deploy backup (document the data loss window).
  - Never roll back by force-pushing an image tag.

--------------------------------------------------------------------------------
MONITORING AND OPERATIONS
--------------------------------------------------------------------------------
  - Uptime check on /api/health/ and / from inside the network every minute.
  - Container restart alerts, disk usage > 80%, Postgres connections > 80% of
    max, Celery queue depth > 500, failed jobs in the last 15 minutes.
  - Log aggregation with retention 30 days; redact tokens and passwords.
  - Dashboards: request rate, p95 latency, 5xx rate, worker failures, mail
    failures, webhook failures.
  - Alerts route to the on-call channel; test one alert end to end.
  - A runbook for: service down, database full, queue backlog, TLS expiry,
    certificate renewal, disk full, SMTP failure, high error rate.
